## 1. Convex vs Non-Convex Functions

### The idea
A **convex** function has exactly one "bowl" — no matter where you start, walking downhill always leads to the single lowest point (the global minimum). A **non-convex** function can have multiple dips and bumps — bowls within bowls — so where you start can determine where you end up.

### Relatable analogy
A convex function is like a single smooth mixing bowl on a table — drop a marble anywhere on the inside, and it always rolls to the same center point. A non-convex function is like an egg carton — drop a marble in, and it settles into *whichever* dimple it happened to land near, not necessarily the deepest one in the whole carton.

### Where it shows up in ML
- **Linear regression and logistic regression** have convex loss surfaces — gradient descent is guaranteed to find the best solution, no matter where you start.
- **Neural networks have highly non-convex loss surfaces** — millions of dimples. This is *why* things like random weight initialization, learning rate schedules, and momentum matter so much: you're trying to land in a good dimple, not necessarily the mathematically perfect one (and in practice, "good enough" dimples work remarkably well).

### Exercises
1. **By hand:** Sketch `f(x) = x²` (convex) and `f(x) = x⁴ - 4x² ` (non-convex — it has two dips) on paper for `x` between -3 and 3. Mark where you think the minima are on each.
2. **NumPy — visualize both:**
   ```python
   import numpy as np
   import matplotlib.pyplot as plt

   x = np.linspace(-3, 3, 200)
   convex = x**2
   non_convex = x**4 - 4*x**2

   fig, axs = plt.subplots(1, 2, figsize=(10, 4))
   axs[0].plot(x, convex); axs[0].set_title("Convex: one minimum")
   axs[1].plot(x, non_convex); axs[1].set_title("Non-convex: two minima")
   plt.show()
   ```

## 2. Local Minima, Global Minima & Saddle Points

### The idea
- **Global minimum**: the single lowest point across the *entire* function.
- **Local minimum**: a point that's lower than all its immediate neighbors, but not necessarily the lowest point overall — like a dimple in the egg carton that isn't the deepest one.
- **Saddle point**: a point where the surface is flat (gradient ≈ 0) but it's not actually a minimum — it curves up in one direction and down in another, like a horse's saddle. Gradient descent can slow to a crawl here, mistaking "flat" for "done."

### Relatable analogy
Imagine hiking down a mountain range in fog, looking for the lowest valley. You might walk into a valley that feels like the bottom (a local minimum) — flat ground all around your immediate area — without realizing there's a much deeper valley two ridges over (the global minimum) that you can't see because of the fog. A saddle point is like standing on a mountain pass: flat in the direction you're walking, but it drops away steeply to your left and right — easy to mistake for "I've arrived" if you're only checking the ground right under your feet.

### Where it shows up in ML
- Training a neural network essentially never guarantees finding the *global* minimum — practitioners aim for a "good enough" local minimum, and in high-dimensional deep learning, research suggests most local minima found in practice are actually quite good.
- Saddle points are a bigger practical nuisance in high dimensions than bad local minima — a lot of optimizer design (momentum, Adam) exists specifically to power through flat/saddle regions instead of getting stuck.

### Exercises
1. **By hand (conceptual):** For `f(x) = x⁴ - 4x²` from Section 1, find where `f'(x) = 0` (take the derivative, set it to zero, solve for x). You should find 3 points — which are minima, and which is neither a min nor max?
2. **NumPy — locate the flat points numerically:**
   ```python
   import numpy as np

   def f(x):
       return x**4 - 4*x**2

   def fprime(x):
       return 4*x**3 - 8*x

   for x in np.linspace(-3, 3, 13):
       if abs(fprime(x)) < 0.5:
           print(f"Near-flat region around x={x:.2f}, f(x)={f(x):.2f}")
   ```
3. **Reflect:** Why might a "flat" region (where the gradient is near zero) make plain gradient descent take a very long time to escape, even if it's not actually a minimum? (Hint: think about how big a step gradient descent takes when the gradient itself is tiny.)

## 3. Learning Rate

### The idea
The learning rate is the size of each step gradient descent takes when moving "downhill." Too small, and training crawls forever. Too large, and you overshoot the minimum — potentially bouncing around wildly or diverging entirely.

### Relatable analogy
Think of trying to park a car in a tight spot by pumping the gas. Tiny taps on the gas (small learning rate) get you there eventually, but very slowly. Flooring it (large learning rate) might make you overshoot the spot completely, then overcorrect the other way, then overcorrect again — never quite settling.

### Where it shows up in ML
- Learning rate is one of the single most important hyperparameters in all of deep learning. Get it wrong and even a perfectly good model architecture will fail to train.
- **Learning rate schedules** (starting large and shrinking over time) are standard practice — take big confident steps early when you're far from the minimum, then smaller careful steps as you get close, to avoid overshooting.

### Exercises
1. **NumPy — feel the effect of learning rate directly:**
   ```python
   import numpy as np

   def f(x):
       return x**2

   def fprime(x):
       return 2*x

   def run_gd(lr, steps=15, start=5.0):
       x = start
       history = [x]
       for _ in range(steps):
           x = x - lr * fprime(x)
           history.append(x)
       return history

   for lr in [0.01, 0.1, 0.9, 1.01]:
       print(f"\nlearning rate = {lr}")
       print([round(v, 3) for v in run_gd(lr)])
   ```
2. **Reflect:** Which learning rate(s) above converge smoothly? Which one crawls? Which one oscillates or blows up? Try to predict the pattern before running the code, then check.
3. **Plot it:** For each learning rate, plot `x` value against step number. You should see a smooth converging curve, a very slow creeping curve, and a wildly oscillating (or exploding) curve.

## 4. Stochastic Gradient Descent (SGD)

### The idea
"Vanilla" (batch) gradient descent computes the gradient using your *entire* dataset before taking a single step — accurate, but slow if you have millions of data points. **Stochastic Gradient Descent** instead estimates the gradient using just *one* (or a small batch of) randomly chosen data points per step. It's a noisier, faster way to get roughly the same direction, taking many more (cheaper) steps instead of few (expensive) ones.

### Relatable analogy
Imagine you want to know the average height of everyone in your city, to decide how tall to build doorways. Batch gradient descent is like measuring literally every single person before making any decision — accurate but painfully slow. SGD is like asking one random passerby at a time, adjusting your estimate a little after each person — noisier and jumpier, but you can start adjusting immediately and you'll still converge to roughly the right answer, much faster overall.

### Where it shows up in ML
- Virtually all deep learning training uses SGD or a variant of it (with "mini-batches" — a middle ground between one sample and the whole dataset) because datasets are far too large to compute a full-batch gradient at every step.
- The "noise" in SGD isn't purely a downside — it can actually help the optimizer bounce out of shallow local minima and saddle points, since each step is only an approximation and doesn't perfectly follow the exact surface.

### Exercises
1. **NumPy — compare batch GD vs SGD on linear regression:**
   ```python
   import numpy as np

   np.random.seed(0)
   X = np.linspace(0, 10, 200)
   y = 2 * X + 1 + np.random.normal(0, 1, size=X.shape)

   # --- Batch Gradient Descent ---
   w, b = 0.0, 0.0
   lr = 0.01
   for epoch in range(50):
       y_pred = w * X + b
       error = y_pred - y
       dw = (2/len(X)) * np.sum(error * X)
       db = (2/len(X)) * np.sum(error)
       w -= lr * dw
       b -= lr * db
   print(f"Batch GD result: w={w:.3f}, b={b:.3f}")

   # --- Stochastic Gradient Descent (1 sample per step) ---
   w, b = 0.0, 0.0
   lr = 0.01
   for epoch in range(50):
       indices = np.random.permutation(len(X))
       for i in indices:
           xi, yi = X[i], y[i]
           y_pred = w * xi + b
           error = y_pred - yi
           dw = 2 * error * xi
           db = 2 * error
           w -= lr * dw
           b -= lr * db
   print(f"SGD result: w={w:.3f}, b={b:.3f}")
   ```
2. **Reflect:** Both should land near `w≈2, b≈1`. Which approach took more individual weight-update steps? Which do you think would scale better to a dataset with 10 million rows, and why?
3. **Plot the difference:** Track and plot the loss value after every *epoch* for both methods. Batch GD's loss curve should be smooth; SGD's should be noisier but trend the same direction.

## 5. Momentum

### The idea
Momentum adds "memory" to gradient descent: instead of only looking at the current gradient, it also considers the direction it's been moving in recent steps, and keeps some of that velocity. This smooths out noisy zig-zagging and helps push through flat regions and shallow local minima/saddle points.

### Relatable analogy
Plain gradient descent is like walking downhill, stopping completely, checking the slope, taking one step, stopping completely again, checking again — cautious but slow, and easily fooled by small bumps. Momentum is like *rolling* a ball downhill: it builds up speed in the direction it's consistently been heading, so small bumps and flat patches don't stop it — it carries through them using accumulated momentum, the same way a real ball would.

### Where it shows up in ML
- Almost every modern optimizer (Momentum SGD, Adam, RMSprop) builds on this idea. It's one of the simplest, highest-impact tweaks you can make to vanilla gradient descent.
- Particularly useful for narrow, curved valleys in the loss surface, where vanilla gradient descent tends to zig-zag back and forth across the valley walls instead of smoothly heading down the valley floor.

### Exercises
1. **NumPy — implement Momentum from scratch and compare to vanilla GD:**
   ```python
   import numpy as np

   # A "narrow valley" loss surface: steep in y, shallow in x
   def f(x, y):
       return 0.1 * x**2 + 5 * y**2

   def grad(x, y):
       return np.array([0.2*x, 10*y])

   # --- Vanilla Gradient Descent ---
   point = np.array([-8.0, 3.0])
   lr = 0.08
   path_vanilla = [point.copy()]
   for _ in range(30):
       point = point - lr * grad(point[0], point[1])
       path_vanilla.append(point.copy())

   # --- Gradient Descent with Momentum ---
   point = np.array([-8.0, 3.0])
   velocity = np.array([0.0, 0.0])
   beta = 0.9  # how much past velocity to keep
   path_momentum = [point.copy()]
   for _ in range(30):
       g = grad(point[0], point[1])
       velocity = beta * velocity - lr * g
       point = point + velocity
       path_momentum.append(point.copy())

   print("Vanilla GD final point:", path_vanilla[-1])
   print("Momentum final point:", path_momentum[-1])
   ```
2. **Plot both paths:** Convert `path_vanilla` and `path_momentum` to NumPy arrays and plot their `x, y` trajectories on the same graph (maybe with a contour plot of `f` underneath, using `plt.contour`). Notice how vanilla GD zig-zags across the narrow valley while momentum smooths the path.
3. **Experiment:** Try `beta = 0.0` (no momentum, should match vanilla), `beta = 0.5`, and `beta = 0.99`. How does the path change? At what point does too much momentum start to overshoot?

## 6. Adam Optimizer (Conceptual Overview)

### The idea
Adam ("Adaptive Moment Estimation") combines two ideas: (1) momentum — remembering the direction you've been heading — and (2) **adaptive learning rates** — automatically taking bigger steps for parameters that have historically had small/consistent gradients, and smaller, more cautious steps for parameters with large or erratic gradients. Each parameter effectively gets its own personalized learning rate that adjusts over time.

### Relatable analogy
Imagine you're adjusting many different dials on a soundboard to get the perfect mix. Some dials (like "master volume") need small careful nudges — you're always close to the right value and don't want to overshoot. Other dials (like an untouched EQ knob) might need big, confident swings because you're starting far from where you need to be, and past adjustments there have been small and predictable. Adam is like an assistant who watches how you've been adjusting each dial and automatically decides "this dial needs a big turn, that one needs a tiny nudge" — without you telling it explicitly, dial by dial.

### Where it shows up in ML
- Adam is the default, go-to optimizer for training most deep learning models today (you'll implement and tune it directly in Phase 5). It's popular because it "just works" reasonably well across a wide range of problems with minimal tuning, combining the benefits of momentum and per-parameter adaptive step sizes.
- You don't need to hand-derive Adam's full update equations right now — the important thing at this stage is understanding *why* it exists: momentum (smoothing/pushing through flat spots) + adaptive rates (not treating every parameter identically).

### Exercises
1. **Conceptual:** In the "narrow valley" example from Section 5 (`f(x, y) = 0.1x² + 5y²`), the `x` direction is shallow (needs bigger steps) and the `y` direction is steep (needs smaller, more careful steps). Explain in your own words why a *single, shared* learning rate for both `x` and `y` is a fundamentally awkward fit for this surface — and why per-parameter adaptive rates (Adam's core idea) would help.
2. **Python — use a real Adam optimizer and compare convergence speed:**
   ```python
   # This uses PyTorch just to *observe* Adam's behavior — full PyTorch mechanics come in Phase 5.
   # If PyTorch isn't installed: pip install torch --break-system-packages
   import torch

   def loss_fn(params):
       x, y = params[0], params[1]
       return 0.1 * x**2 + 5 * y**2

   params = torch.tensor([-8.0, 3.0], requires_grad=True)
   optimizer = torch.optim.Adam([params], lr=0.3)

   for step in range(30):
       optimizer.zero_grad()
       loss = loss_fn(params)
       loss.backward()
       optimizer.step()

   print("Adam final point:", params.detach().numpy())
   ```
   Compare how few steps Adam needed here versus your vanilla GD and Momentum runs in Section 5 to reach a similarly small point.
3. **Reflect:** Adam tends to converge fast and requires less learning-rate tuning than vanilla SGD — so why do many state-of-the-art results still sometimes report using plain SGD with momentum instead of Adam?
