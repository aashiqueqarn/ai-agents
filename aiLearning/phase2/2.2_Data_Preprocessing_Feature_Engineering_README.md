## 1. Handling Missing Data (Imputation)

### The idea
Real datasets almost always have gaps — a sensor that failed to log a reading, a customer who skipped an optional form field, a survey response left blank. **Imputation** is the practice of filling in those gaps sensibly (rather than just deleting anything incomplete), because throwing away every row with a single missing value can waste a huge amount of otherwise-good data.

### Relatable analogy
Imagine a class attendance register where a few students forgot to write their marks for one quiz. You wouldn't throw out the *entire* student's record just because of one missing quiz score — you might fill it in with the class average for that quiz, or with that student's average across other quizzes, or simply mark it as "absent" if that's meaningful. Which approach makes sense depends on *why* the data is missing — and that judgment call is the real skill here, not just picking a formula.

### Where it shows up in ML
- Nearly every real dataset (customer records, sensor logs, medical data, surveys) has missing values before it ever reaches a model.
- Choosing the *wrong* imputation strategy can quietly inject bias — e.g., filling missing income with the overall average can make low-income customers look wealthier than they are, skewing predictions.

### Exercises
1. **By hand (conceptual):** A dataset of house listings has a `garage_size` column that's missing for 30% of rows. What are two different reasons this might be missing — and would the "right" way to fill it in differ depending on the reason? (Hint: "missing because the house genuinely has no garage" vs. "missing because the field wasn't filled in by mistake" call for very different fixes.)
2. **Pandas — inspect and impute:**
   ```python
   import pandas as pd
   import numpy as np

   df = pd.DataFrame({
       "age": [25, np.nan, 35, 40, np.nan, 22],
       "income": [50000, 60000, np.nan, 80000, 45000, np.nan],
       "city": ["Patna", "Delhi", "Patna", np.nan, "Mumbai", "Delhi"]
   })

   print(df.isnull().sum())  # how many missing per column

   # Fill numeric columns with the median (robust to outliers)
   df["age"] = df["age"].fillna(df["age"].median())
   df["income"] = df["income"].fillna(df["income"].median())

   # Fill categorical column with the most frequent value (mode)
   df["city"] = df["city"].fillna(df["city"].mode()[0])

   print(df)
   ```
3. **scikit-learn — the standard tool for this:**
   ```python
   from sklearn.impute import SimpleImputer
   import pandas as pd
   import numpy as np

   df = pd.DataFrame({"age": [25, np.nan, 35, 40, np.nan, 22]})
   imputer = SimpleImputer(strategy="mean")   # try "median", "most_frequent" too
   df["age_imputed"] = imputer.fit_transform(df[["age"]])
   print(df)
   ```
4. **Reflect:** Why might filling a missing value with the **mean** be a poor choice for a column with extreme outliers, and the **median** a safer default? (Connects back to Topic 1.3's discussion of how outliers distort averages.)

## 2. Encoding Categorical Variables

### The idea
Models do math — they need numbers, not text labels like "Delhi" or "Small/Medium/Large." **Encoding** converts categorical (text/label) columns into numeric form so a model can use them. Different encoding styles fit different situations:
- **One-hot encoding**: create a separate 0/1 column for each category (e.g., `is_Delhi`, `is_Mumbai`, `is_Patna`). Best for categories with *no* natural order.
- **Label encoding**: assign each category an integer (Delhi=0, Mumbai=1, Patna=2). Simple, but implies a false ordering unless the categories genuinely *are* ordered.
- **Ordinal encoding**: like label encoding, but used deliberately when there *is* a real order (Small=0, Medium=1, Large=2).
- **Target encoding**: replace each category with a number derived from the target variable (e.g., replace city name with the average purchase amount for that city). Powerful but risks leaking target information if done carelessly.

### Relatable analogy
Imagine sorting mail into bins. One-hot encoding is like giving every city its *own separate bin* — a letter either goes in the "Delhi" bin (1) or it doesn't (0), no city is "more" than another. Label/ordinal encoding is like writing a number on each letter based on priority — fine when there's a genuine ranking (like shirt sizes S/M/L), but misleading if you numbered cities 0, 1, 2 as if Mumbai were somehow "more" than Delhi just because it got a bigger number.

### Where it shows up in ML
- Almost every real dataset has categorical columns (city, product category, job title, education level) — you cannot feed these directly into most ML algorithms without encoding them first.
- Picking the wrong encoding is a classic beginner mistake: label-encoding a genuinely unordered category (like city names) can trick a model into learning a fake numeric relationship that doesn't exist ("Mumbai (2) is twice Delhi (1)" means nothing).

### Exercises
1. **By hand (conceptual):** For a `shirt_size` column with values Small/Medium/Large, and a `favorite_color` column with values Red/Blue/Green, which encoding (one-hot vs ordinal) fits each column better, and why?
2. **Pandas/scikit-learn — one-hot encoding:**
   ```python
   import pandas as pd

   df = pd.DataFrame({"city": ["Delhi", "Mumbai", "Patna", "Delhi", "Mumbai"]})
   one_hot = pd.get_dummies(df["city"], prefix="city")
   print(one_hot)
   ```
3. **scikit-learn — label/ordinal encoding:**
   ```python
   from sklearn.preprocessing import OrdinalEncoder

   df = pd.DataFrame({"shirt_size": ["Small", "Large", "Medium", "Small", "Large"]})
   encoder = OrdinalEncoder(categories=[["Small", "Medium", "Large"]])  # explicit order matters!
   df["size_encoded"] = encoder.fit_transform(df[["shirt_size"]])
   print(df)
   ```
4. **Target encoding (conceptual + mini implementation):**
   ```python
   import pandas as pd

   df = pd.DataFrame({
       "city": ["Delhi", "Mumbai", "Delhi", "Patna", "Mumbai", "Patna"],
       "purchase_amount": [500, 800, 600, 200, 900, 250]
   })

   city_avg = df.groupby("city")["purchase_amount"].mean()
   df["city_target_encoded"] = df["city"].map(city_avg)
   print(df)
   ```
   **Reflect:** Why is target encoding risky if you compute the averages using your *entire* dataset (including the row you're encoding) rather than excluding that row or using only training data? (This is a common source of "data leakage" — a topic that will matter a lot from Phase 3 onward.)

## 3. Feature Scaling (Standardization & Normalization)

### The idea
Many ML algorithms are sensitive to the *scale* of your features. If one column ranges from 0-1 (like a probability) and another ranges from 0-500,000 (like income), the large-scale column can dominate calculations simply because its numbers are bigger — not because it's actually more important. **Scaling** puts all features on a comparable footing.
- **Standardization** (a.k.a. Z-score scaling): rescale so each column has mean 0 and standard deviation 1. Formula: `(x - mean) / std`.
- **Normalization** (a.k.a. Min-Max scaling): rescale so each column's values fall between 0 and 1. Formula: `(x - min) / (max - min)`.

### Relatable analogy
Imagine judging a talent competition where one judge scores out of 10 and another scores out of 1,000. If you just add their raw scores together, the second judge's opinion will completely drown out the first judge's, purely because of the number range — not because their judgment is more valuable. Scaling is like converting both judges' scores onto the *same* scale (say, both out of 100) before combining them, so each judge's opinion actually counts proportionally.

### Where it shows up in ML
- **Distance-based algorithms** (k-NN, k-means clustering, SVMs) are directly affected by scale — an unscaled "income" column can completely dominate distance calculations over an unscaled "age" column just because its numbers are thousands of times bigger.
- **Gradient descent** (Topic 1.4) converges much faster and more reliably on scaled features — unscaled data with wildly different ranges creates a loss surface shaped like a long narrow valley (remember the "narrow valley" momentum example?), which is exactly the hard case for optimizers.
- Tree-based models (decision trees, random forests, XGBoost) are a notable exception — they're generally *not* sensitive to feature scale, since they split on thresholds rather than compute distances.

### Exercises
1. **By hand:** For the column `[10, 20, 30, 40, 50]`, compute the standardized version (subtract the mean, divide by the standard deviation) for at least two values. Then compute the normalized (min-max) version for the same two values.
2. **scikit-learn:**
   ```python
   from sklearn.preprocessing import StandardScaler, MinMaxScaler
   import pandas as pd

   df = pd.DataFrame({
       "age": [22, 25, 47, 35, 46],
       "income": [25000, 32000, 95000, 60000, 52000]
   })

   standard_scaler = StandardScaler()
   df_standardized = pd.DataFrame(standard_scaler.fit_transform(df), columns=df.columns)
   print("Standardized:\n", df_standardized)

   minmax_scaler = MinMaxScaler()
   df_normalized = pd.DataFrame(minmax_scaler.fit_transform(df), columns=df.columns)
   print("\nNormalized:\n", df_normalized)
   ```
3. **Reflect:** After standardizing, verify (with `.mean()` and `.std()`) that each column really does have mean ≈ 0 and std ≈ 1. After normalizing, verify each column's min and max are 0 and 1.
4. **Important gotcha:** Why must you `.fit()` the scaler *only* on training data, and then just `.transform()` (not re-fit) the validation/test data? What real-world problem would you cause if you fit the scaler on the full dataset before splitting?

## 4. Feature Selection

### The idea
Not every column in your dataset is actually useful — some are irrelevant noise, some are redundant (basically saying the same thing as another column), and having too many can make models slower, harder to interpret, and prone to overfitting (memorizing noise instead of learning real patterns — you'll meet this formally in Phase 3). **Feature selection** is the process of choosing which features actually earn their place in the model.

### Relatable analogy
Imagine you're diagnosing a car problem and a mechanic hands you a 50-page printout of every sensor reading from the last month. Most of it is irrelevant to today's issue. A good mechanic knows which 3-4 readings actually matter for the symptom you're describing, and ignores the rest — not because the other readings are wrong, but because they add noise rather than insight for *this* diagnosis.

### Where it shows up in ML
- **Fewer, more relevant features** often produce a model that's faster to train, easier to explain to stakeholders, and less likely to overfit.
- Feature selection is especially important in domains with huge numbers of raw columns relative to the number of rows — like genomics or certain sensor/IoT datasets — where "too many features, not enough data" is a real risk.

### Exercises
1. **Correlation-based selection (simple but useful):**
   ```python
   import pandas as pd
   import numpy as np

   np.random.seed(0)
   df = pd.DataFrame({
       "feature_a": np.random.rand(100),
       "feature_b": np.random.rand(100),
   })
   df["feature_c"] = df["feature_a"] * 2 + np.random.normal(0, 0.01, 100)  # nearly identical to feature_a
   df["target"] = df["feature_a"] * 3 + np.random.normal(0, 0.1, 100)

   print(df.corr()["target"].sort_values(ascending=False))
   ```
   Which feature correlates most with `target`? Which two features are so similar to each other that keeping both is likely redundant?
2. **scikit-learn — automatic feature importance from a model:**
   ```python
   from sklearn.ensemble import RandomForestRegressor
   import pandas as pd
   import numpy as np

   np.random.seed(0)
   X = pd.DataFrame({
       "useful_feature": np.random.rand(200),
       "noisy_feature": np.random.rand(200),
   })
   y = X["useful_feature"] * 5 + np.random.normal(0, 0.1, 200)

   model = RandomForestRegressor(random_state=0)
   model.fit(X, y)
   importances = pd.Series(model.feature_importances_, index=X.columns)
   print(importances.sort_values(ascending=False))
   ```
   Does `useful_feature` come out with much higher importance than `noisy_feature`, as expected?
3. **Reflect:** Why is dropping a highly-correlated *redundant* feature (Exercise 1's `feature_c`) usually safe, while dropping a feature that seems weakly correlated with the target in isolation can sometimes still be a mistake? (Hint: think about features that only matter in *combination* with another feature — this is a preview of why feature selection isn't always as simple as "keep the top correlations.")

## 5. Handling Imbalanced Datasets (SMOTE, Class Weights)

### The idea
An imbalanced dataset is one where one class vastly outnumbers another — e.g., 99% "not fraud" and 1% "fraud" transactions. A model trained naively on this can achieve 99% accuracy by simply *always predicting "not fraud"* — technically accurate, but completely useless, since it never catches the rare cases you actually care about. Two common fixes:
- **Class weights**: tell the model to "pay more attention" to mistakes on the minority class during training, by penalizing those errors more heavily.
- **SMOTE** (Synthetic Minority Oversampling Technique): generate new, synthetic examples of the minority class (interpolated between existing minority examples) so the model sees more balanced training data.

### Relatable analogy
Imagine training a security guard to spot shoplifters, where shoplifters make up 1 in 1,000 customers. If the guard just assumes "nobody is ever a shoplifter," they'll be right 99.9% of the time by raw accuracy — but they'll catch precisely zero shoplifters, which defeats the entire point of having a guard. A better approach is deliberately showing the guard *many more examples* of shoplifting behavior during training (even staged/synthetic ones — like SMOTE) or explicitly telling them "missing a shoplifter is a much bigger deal than a false alarm" (like class weights) — so they actually learn to notice the rare, important case.

### Where it shows up in ML
- **Fraud detection, disease diagnosis, manufacturing defect detection, churn prediction** — almost every high-value real-world classification problem is naturally imbalanced, because the interesting event (fraud, disease, defect, churn) is rare by definition.
- Accuracy becomes a misleading metric on imbalanced data — this is exactly why metrics like precision, recall, and F1-score (which you'll meet in Phase 3) matter so much more than plain accuracy for these problems.

### Exercises
1. **See the trap yourself:**
   ```python
   import numpy as np
   from sklearn.linear_model import LogisticRegression
   from sklearn.metrics import accuracy_score, confusion_matrix

   np.random.seed(0)
   n = 1000
   X = np.random.rand(n, 2)
   y = np.zeros(n)
   y[:10] = 1  # only 1% positive class ("fraud")
   np.random.shuffle(y)

   model = LogisticRegression()
   model.fit(X, y)
   preds = model.predict(X)

   print("Accuracy:", accuracy_score(y, preds))
   print("Confusion matrix:\n", confusion_matrix(y, preds))
   ```
   Look at the confusion matrix: how many of the actual minority-class (1) cases did the model correctly catch? Is the "impressive" accuracy number actually meaningful here?
2. **Fix with class weights:**
   ```python
   model_weighted = LogisticRegression(class_weight="balanced")
   model_weighted.fit(X, y)
   preds_weighted = model_weighted.predict(X)

   print("Weighted accuracy:", accuracy_score(y, preds_weighted))
   print("Weighted confusion matrix:\n", confusion_matrix(y, preds_weighted))
   ```
   Did the model catch more of the minority class this time, even if overall accuracy went down? Why might that be a good trade?
3. **SMOTE (requires `pip install imbalanced-learn --break-system-packages`):**
   ```python
   from imblearn.over_sampling import SMOTE
   import numpy as np

   np.random.seed(0)
   X = np.random.rand(1000, 2)
   y = np.zeros(1000)
   y[:10] = 1

   print("Before SMOTE:", np.bincount(y.astype(int)))
   X_resampled, y_resampled = SMOTE(random_state=0).fit_resample(X, y)
   print("After SMOTE:", np.bincount(y_resampled.astype(int)))
   ```
4. **Reflect:** Why should SMOTE be applied only to the *training* set, never to your validation/test set? (Hint: your test set needs to reflect the real-world imbalance you'll actually face in production — synthetic examples there would give you a falsely rosy performance estimate.)

## 6. Outlier Detection

### The idea
An outlier is a data point that differs dramatically from the rest of the dataset — it might be a genuine rare event, a data entry error, or a sensor glitch. **Outlier detection** is about finding these points so you can decide, deliberately, what to do with them (keep, investigate, cap, or remove) rather than letting them silently distort your analysis or model.

### Relatable analogy
Imagine checking a class's test scores and seeing one student scored "-5" and another scored "1000" on a test out of 100. These aren't just "impressively bad" or "impressively good" — they're almost certainly data entry mistakes worth investigating, not genuine performances to learn from. But context matters: if you're looking at *income* data and see one person earning 100x the median, that could be a perfectly real (if rare) high earner, not an error — the same statistical "outlier" label calls for very different handling depending on what's actually true about the world.

### Where it shows up in ML
- Outliers can badly skew statistics like the mean (Topic 1.3) and can dominate loss functions like MSE (Topic 1.2), since squared error punishes large deviations disproportionately — a few extreme outliers can quietly warp an entire model's training.
- Outlier detection is a routine, essential step in EDA (Topic 2.1) — it's often where you catch real data quality bugs before they contaminate downstream analysis.

### Exercises
1. **IQR method (a classic, simple, interpretable approach):**
   ```python
   import pandas as pd
   import numpy as np

   data = pd.Series([12, 14, 15, 15, 16, 18, 19, 20, 21, 100])  # 100 looks suspicious

   Q1 = data.quantile(0.25)
   Q3 = data.quantile(0.75)
   IQR = Q3 - Q1
   lower_bound = Q1 - 1.5 * IQR
   upper_bound = Q3 + 1.5 * IQR

   outliers = data[(data < lower_bound) | (data > upper_bound)]
   print("Outliers:", outliers.tolist())
   ```
2. **Visual detection with a boxplot:**
   ```python
   import seaborn as sns
   import matplotlib.pyplot as plt

   sns.boxplot(x=data)
   plt.title("Boxplot — dots beyond the whiskers are flagged outliers")
   plt.show()
   ```
3. **Z-score method (uses the standardization idea from Section 3):**
   ```python
   from scipy import stats
   import numpy as np

   z_scores = np.abs(stats.zscore(data))
   outliers_z = data[z_scores > 2]   # commonly 2 or 3 standard deviations away
   print("Outliers (z-score method):", outliers_z.tolist())
   ```
4. **Reflect:** For a genuinely skewed real-world variable like income or house prices, would you expect the IQR or z-score method to flag *too many* "outliers" that are actually normal? Why might a domain-aware cutoff (or a transform like `log(income)` before detecting outliers) work better than a purely statistical rule in such cases?
